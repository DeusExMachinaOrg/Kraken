**How to read this.** Each cluster lists its implementation items, then the verification

## Cluster: bodies-constraints

### Summary

This cluster is the measurement rig for Stage 1 mode 4 — eleven `wm4_*` levers that exist now only as entries in the recovered `Config::Config()` table (`docs/recovered/binary/mined/config-members.txt`), values in `docs/recovered/binary/kraken.ini`, and printf format strings in `docs/recovered/binary/mined/formats.tsv`. None of them is in `docs/wheel-dof-stage1-plan.md` except as rollback-flag names in plan line 326 and the dt clamp in line 383, so the plan is NOT the spec here; the format strings and `docs/recovered/sec96-wheel-mass-fix.md` are. Three of the eleven are floats (`wm4_resync_period`, `wm4_max_dt`, `wm4_compress_fraction`) whose compiled defaults are unrecoverable — take values from kraken.ini and treat bounds as unknown; the other eight are integers whose defaults and bounds in config-members.txt are authoritative. The centrepiece is the §82 resync divergence instrument: every `wm4_resync_period` seconds it re-seats the Jolt shadow onto ODE's pose, emits one line carrying the window's peak up-vector error, peak COM error, the accumulated ODE tilt disturbance and their ratio, then emits a RESIDUAL line proving the window started from zero. The divergence analysis regressed `upMax` on `odeTiltPath` across those events; §96 records the liveness test for that regression (intercept and R²) and it must be preserved. `wm4_resync_reseat` (§87) and `wm4_resync_keep_gear` (§88) are sub-levers of that same reseat. `wm4_compress_fraction` splits the suspension range into compression and droop headroom for the SixDOF `TranslationZ` limits and is read back in the §58 wheel-body line and warned about in the §60 line. `wm4_chassis_mass_excl_wheels` is the §96 fix, fully documented including its exact binding check and its refusal path. `wm4_inertia_from_box` (§93) and `wm4_joint_at_mount` (§75) each have a matching diagnostic line. `wm4_hardcore` is a boolean collapse of the plan's three-way flag; `wm4_contact_torque_cap` has no surviving evidence of its meaning at all and is flagged.

#### 2. §82 resync instrument — the periodic re-seat and its window accumulators

- **What:** The core measurement loop. When wm4_resync_period > 0, run a per-vehicle timer; every period seconds, (a) close the current measurement window and emit the resync line, (b) hard re-seat the Jolt shadow onto ODE's current pose (chassis position and orientation, and — under wm4_resync_reseat — the wheel bodies), (c) emit the RESIDUAL line measuring what error survived the re-seat, (d) zero the window accumulators and start the next window. Fields, established from the live log: #%u is a monotonic per-vehicle resync counter starting at 0; dt is the actual elapsed wall time of the window in seconds (prints as 0.50/0.51 when the period is 0.5, so it is measured, not the configured period); upMax is the maximum over the window of the angle in degrees between the Jolt chassis up vector and the ODE chassis up vector (the same quantity as `upDelta` in the §69 tilt line and the §78 attdense line); posMax is the maximum over the window of the distance in metres between Jolt and ODE chassis COM; odeTiltPath is the accumulated path length in degrees of ODE's own tilt over the window — the DISTURBANCE the window contained, i.e. the denominator; gain = upMax / odeTiltPath, verified numerically against 26 log events (e.g. #0 1.758/4.520=0.3888, #1 1.289/0.208=6.1952, #5 1.614/0.906=1.7818, all exact to the printed precision). gain prints the sentinel -1.0000 when odeTiltPath falls below a floor. The RESIDUAL line's pos and up are the same two quantities re-measured immediately AFTER the re-seat; they must read ~0 (observed 0.0000, occasionally 0.0198 deg).
- **Source:** formats.tsv 0x101de0f8 and 0x101de158; live evidence docs/recovered/binary/kraken-20260727-1527.log lines 195/200, 380/385, 609/614 and 33 further events; docs/recovered/README.md line 16 names it "the §82 resync divergence instrument"; sec96-wheel-mass-fix.md §96.3 uses it as the measurement
- **Constants:** wm4_resync_period: kraken.ini value 0.0 (= instrument off). The §96 measurement ran at wm4_resync_period=0.5, stated verbatim in sec96-wheel-mass-fix.md §96.3. gain sentinel value is exactly -1.0000. The odeTiltPath floor below which the sentinel is emitted is bracketed by the log to the open interval (0.037, 0.147) degrees — no surviving source gives the exact number.
- **Log line:** docs §82: resync (%s) #%u dt=%.2fs upMax=%.3f deg posMax=%.3f m odeTiltPath=%.3f deg gain=%.4f
AND
docs §82: resync RESIDUAL (%s) #%u pos=%.4f m up=%.4f deg
- **Pitfall:** The RESIDUAL line is not decoration — it is what makes upMax/posMax attributable to a single window. Emit it AFTER the re-seat and BEFORE clearing the accumulators, and make sure it re-measures rather than reusing the pre-seat values. Second trap: the resync line must be emitted BEFORE the re-seat mutates the pose, otherwise upMax/posMax are read against an already-corrected shadow and the instrument silently reads zero. Third: the ordering in the surviving log is resync line, then the four §87 landing lines, then RESIDUAL (log.txt 195, 196-199, 200) — reproduce that order, because the analysis scripts keyed off adjacency.

#### 3. §82 liveness / dead-instrument acceptance check

- **What:** The divergence analysis this line feeds is a linear regression of upMax (y) on odeTiltPath (x) across all resync events of a run; the reported metric is the SLOPE in deg/deg ("наклон upMax"), with a second regression of posMax on odeTiltPath giving "наклон posMax". The intercept and R² of that fit are the instrument's own health check and must be reported alongside the slope. §96 states the failure signature explicitly: a §87-style DEAD instrument shows intercept > 5 with R² < 0.15; the §96 run was accepted because it showed intercepts 1.83 and 2.12 at R² 0.44 and 0.22. Re-implement the analysis script (divergence_rate.py, lost) to emit slope ± se, intercept, and R², and to refuse to report a slope when the dead signature is present.
- **Source:** sec96-wheel-mass-fix.md §96.3 ("Инструмент жив: перехваты 1.83 и 2.12 при R² 0.44 и 0.22 — это не подпись мёртвого инструмента из §87 (перехват >5 при R²<0.15)") and §96.4
- **Constants:** dead-instrument signature: intercept > 5 AND R² < 0.15. §96 reference numbers, Bug01, n=3, wm4_resync_period=0.5: lever 0 upMax slope 0.778 ±0.093, posMax slope 0.0717 ±0.0217; lever 1 upMax slope 0.956 ±0.182, posMax slope 0.0782 ±0.0161; difference −0.178 ±0.204 (t=−0.9) and −0.006 ±0.027 (t=−0.2). Sensitivity bound at n=3: 2.5·se = 0.51 deg/deg.
- **Log line:** none (this is the analysis side of docs §82: resync ...)
- **Pitfall:** §96.4 names two limits that must be carried forward, not rediscovered: (1) n=3 only excludes effects larger than ~65% of the baseline slope — never write "no effect", write "effect smaller than two thirds of base"; (2) the two arms saw DIFFERENT terrain (disturbance range 0..12.1° vs 0..6.3°), which at n=3 is luck and wrecks comparability of the two regression arms. The design answer already identified is a multi-shadow run where every arm sees one terrain.

#### 4. wm4_resync_reseat — §87 wheel landing

- **What:** Sub-lever of §82, default 1. After the chassis has been teleported onto ODE's pose, re-seat each wheel body so it lands consistently with the new chassis pose instead of being dragged by the SixDOF constraint from wherever it was. It logs one line per wheel. Field meanings, established from the live log: w is the wheel index; pre and post are the signed ground clearance of that wheel in metres before and after the re-seat (negative = penetrating, observed −0.001..−0.010 when correctly seated; a large positive post such as 0.5598 means the re-seat left the wheel airborne and is a failure signature); R is the wheel radius (0.832/0.925 on Scout01, 0.629/0.635 on Bug01, matching the §54 axis-audit R exactly); dY, dRotDeg and |corr| are chassis-level and therefore identical across all wheels of one resync — dY is the vertical component of the chassis position correction in metres, dRotDeg the magnitude of the orientation correction in degrees, |corr| the magnitude of the total chassis position correction in metres. |corr| is numerically the same quantity as the §82 line's posMax (log #0 posMax=0.100 vs |corr|=0.0999; #1 1.006 vs 1.0060; #2 0.779 vs 0.7792) — it is the cross-check between the two lines.
- **Source:** formats.tsv 0x101dd790; kraken-20260727-1527.log lines 196-199, 381-384, 610-613, 731-734, 891-894; docs/recovered/README.md line 16 names it "§87 wheel re-seating"
- **Constants:** default 1 (config-members +0x530, bounds [0,1])
- **Log line:** docs §87: resync landing (player) w=%zu pre=%.4f post=%.4f m R=%.3f dY=%.4f dRotDeg=%.2f |corr|=%.4f m
- **Pitfall:** "(player)" is LITERAL text in this format string, not a %s — unlike §82, §58, §93 and §75 which all take a vehicle-name %s. This line was emitted for the player vehicle only. Reproduce it that way; making it generic changes the text and breaks any parser written against it. Second trap: §96 refers to §87 as the source of the dead-instrument signature (intercept > 5 at R² < 0.15), i.e. §87 is a known case of a reseat whose regression went dead — treat a run whose §87 post values drift positive as suspect before trusting its §82 slope.

#### 6. wm4_max_dt + wm4_max_substeps — the dt clamp and its readout

- **What:** Sub-step the Jolt update so the explicit tyre spring is never integrated at a frame dt that destabilises it. Per frame, compute n = clamp(ceil(dt / max_dt), 1, wm4_max_substeps) and run that many sub-steps of dt/n (or of max_dt with a remainder), accumulating n into a running average that is printed as substeps_per_frame in the [jolt_profile] line. Measured behaviour of the surviving build, from six §96 run logs paired against their perf lines: the effective sub-step length is a very stable ~3.0 ms — 8.989/2.91, 9.250/3.13, 9.932/3.14, 10.480/3.51, 9.813/3.19, 10.764/3.59, 9.492/3.26 ms per substep — consistent with a ceil rule at a target step of about 1/300 s, and the cap is visible on hitch frames (avg_frame_ms 23.4 with substeps 5.16 under a cap of 8).
- **Source:** plan line 383 (the risk that forced this: ω_n·dt = √(k_t/m_u)·dt is 1.74 at 60 fps but ≈5.2 at 20 fps and ≈6.3 at 17 fps, past the explicit-scheme limit; "ОБЯЗАТЕЛЬНО: кламп dt (jolt_wm4_max_dt, старт 1/30) либо фиксированный подшаг"); plan line 326 lists jolt_wm4_max_dt as a rollback flag; formats.tsv 0x101ddf68 carries substeps_per_frame; docs/recovered/harness/band95.py lines 50/53/183-189 sweep wm4_max_dt as argv[4] with baseline 0.0 and pin wm4_max_substeps=8
- **Constants:** wm4_max_substeps: default 4, bounds [1,16] (integer, authoritative). kraken.ini value 8 and band95.py's pin of 8 are session settings, not the default. wm4_max_dt: kraken.ini value 0.000000; compiled default and bounds not recoverable. The plan's suggested start value is 1/30 s, which the observed ~3 ms sub-step contradicts. Do NOT hardcode 1/300 — it is a measurement off four profile lines, not a quoted constant.
- **Log line:** [jolt_profile] ode_step_avg_ms=%.2f jolt_total_avg_ms=%.2f | physics_update_avg_ms=%.2f wheelmodel_avg_ms=%.2f mirror_avg_ms=%.2f applyvehicle_avg_ms=%.2f applyvehicle_calls_per_frame=%.2f | contact_pairs_per_frame=%.1f contact_points_per_frame=%.1f active_bodies_per_frame=%.1f substeps_per_frame=%.2f | frames=%llu
- **Pitfall:** The meaning of wm4_max_dt = 0 is genuinely ambiguous and it matters. band95.py's BASE_INI pins it to 0 as the baseline arm, which reads as "off"; but the §96 run logs — which came from the last build — show substeps_per_frame of 2.90..5.48, i.e. sub-stepping was active, and the kraken.ini safe state also reads 0.000000. If 0 meant "off", the shipped safe config would have no dt clamp at all, directly against plan line 383. The consistent reading is 0 = "auto, use the built-in target", >0 = pin the ceiling explicitly. Decide this deliberately and write it down; guessing "off" silently removes the stability guarantee that the whole explicit tyre spring rests on. Also: substeps_per_frame is an AVERAGE over the profile window and will read non-integer — do not assert it is integral.

#### 7. wm4_compress_fraction — travel split for the SixDOF TranslationZ limits

- **What:** Splits the suspension travel range between compression and droop when setting the hard bump stops on the constraint. compressHeadroom = range * wm4_compress_fraction, droopHeadroom = range * (1 - wm4_compress_fraction), and the axis is limited relative to the spawn pose: SetLimitedAxis(TranslationZ, -compressHeadroom, +droopHeadroom). Verified against the live log on two vehicles: Scout01 has range=0.250 (§54 axis-audit) and logs "limits -0.1250..0.1250 rel spawn"; Bug01 and Molokovoz01 have range=1.000 and log "limits -0.5000..0.5000 rel spawn" — both exactly range*0.5 with the ini's fraction of 0.5. Sign convention is fixed by the log: travel is NEGATIVE under compression (travel=-0.0366 with springF=+253N). The §58 wheel-body line is the readout: springF and stopF are the spring and bump-stop forces in newtons (from GetTotalLambdaMotorTranslation()[2]/dt and GetTotalLambdaPosition()[2]/dt per plan lines 108-110), travel is the current axis position relative to spawn, the two limit values are the headrooms just computed, kSusp is the spring rate, and sagPredicted = springF / kSusp (verified: 253/7500 = 0.0337 = the printed sagPredicted; 271/3000 = 0.0903 vs printed 0.0905). frameTrav is the per-frame min..max of travel and frameStopN the per-frame max of stopF — these two fields are §90's per-frame extremes, appended to the §58 line rather than given their own tag.
- **Source:** formats.tsv 0x101dd348 (§58 wheel body) and 0x101dc2b8 (§60); plan line 222 (SetLimitedAxis(TranslationZ, minLen, maxLen) without mLimitsSpringSettings — a hard stop) and line 95 (the axis table); kraken-20260727-1527.log lines 39-42, 149-164, 666-669, 844; docs/recovered/README.md line 16 for "§90 per-frame extremes"
- **Constants:** wm4_compress_fraction: kraken.ini value 0.500000; compiled default and bounds NOT recoverable (float key, config-members row is stale). Observed range values: 0.250 (Scout01), 1.000 (Bug01, Molokovoz01), all from WheelPrototypeInfo. kSusp observed 3000/6000/7500 N/m with cSusp = kSusp/20 in every logged case (7500/375, 3000/150, 6000/300).
- **Log line:** docs §58: wheel body (%s) w=%zu springF=%.0fN stopF=%.0fN travel=%.4f (limits %.4f..%.4f rel spawn) kSusp=%.0f sagPredicted=%.4f | frameTrav=%.4f..%.4f frameStopN=%.0f
AND the §60 warning:
docs §60 (%s): wheel %zu predicted static sag %.3fm EXCEEDS compression headroom %.3fm (range %.3f, fraction %.2f) - it will rest on the bump stop once grounded
- **Pitfall:** The §60 line is the engagement check for this lever and it never fired in the surviving log — that is a passing result, not evidence the check is missing. Implement it: at build time compare sagPredicted against compressHeadroom and warn if it exceeds, because a fraction chosen too small silently parks the vehicle on its bump stops, which reads as "the suspension is too stiff" rather than as a config error. Second trap: the limits are "rel spawn", so the zero of TranslationZ is the spawn pose, not the unloaded rest length — getting this wrong shifts the whole travel window by the static sag.

#### 8. wm4_chassis_mass_excl_wheels — the §96 wheel-mass fix

- **What:** Default 1 = correct behaviour; 0 restores the old double-count and exists only for measurement. In BuildWheelBodies (mode 4 only — mode 2 never enters it and is already mass-correct), accumulate the sum of wheel masses through the loop, then in a POST-PASS after the loop reduce the chassis body's mass by that sum, scaling mass and inertia tensor by the SAME single factor. Post-pass rather than at CreateBody, so the tensor derived from the compound shape (§23.10) is preserved — Jolt got its SHAPE right, only the magnitude was wrong, and the tensor is linear in mass. Order is load-bearing and must be fixed in code: the floor max(unsprungMass, chassisMass/40) is computed on the PRE-subtraction mass, i.e. on the whole-vehicle mass. That is the right basis for a threshold protecting against a pathological wheel/vehicle ratio, and it removes the circular dependency. Refusal instead of silent breakage: if the wheels claim >=90% of the vehicle mass, skip the subtraction and log the §95.4 warning — driving the chassis toward zero mass turns a solver blow-up into "the fix made it unstable". The verification is built into the §58 build line itself: chassisMassFinal + wheelMass must equal chassisMass, otherwise the subtraction did not happen.
- **Source:** docs/recovered/sec96-wheel-mass-fix.md §96.1 and §96.2 in full; sec95-force-site-sweep.md §95.4 for the underlying finding (ai::Vehicle::GetMass() at RVA 0x1d5bd0 returns chassis body mass PLUS every wheel's mass, while the chassis body's own mass comes from Vehicle::_CalcMassForBody and contains no wheels; joltshadow.cpp:2240 set the chassis body to max(vehicle->GetMass(), 100.0f), i.e. already chassis+wheels, and mode 4 then added a body per wheel on top); formats.tsv 0x101dc3e8 and 0x101dc360
- **Constants:** default 1, bounds [0,1] (integer, authoritative). Mass floor divisor 40 — the plan calls it jolt_wm4_wheel_mass_floor_div default 40 (line 326) but it did NOT survive as a config key, so it is hardcoded; confirmed live by massFloor=2.50 at chassisMass=100.0, 3.30 at 132.0, 4.18 at 167.0. Refusal threshold 90%. Existing 100.0f mass floor at joltshadow.cpp:2240 — §95.4 flags it separately as silently inflating any vehicle under 100 kg. Binding table from §96.2: Bug01 chassisMass 132.0, wheelMass 36.0, chassisMassFinal 96.0 (lever 1) vs 132.0 (lever 0); Molokovoz01 167.0 / 44.0 / 123.0 vs 167.0. Error being removed: Bug01 +27.3%, Molokovoz01 +26.3%, Scout01 +6.0%.
- **Log line:** docs §58 (%s): mode 4 - built %zu wheel bodies + SixDOF constraints (chassisMass=%.1f, massFloor=%.2f) | docs §95.4 wheelMass=%.1f chassisMassFinal=%.1f total=%.1f
AND the refusal path:
docs §95.4 (%s): wheel mass %.1f is >=90%% of vehicle mass %.1f - NOT subtracting; the shadow stays heavier than ODE for this vehicle
- **Pitfall:** Keep the default at 1 even though §96.3 measured a null effect (t=−0.9 and t=−0.2) — the reasoning is the same as §88 and §93: the vehicle's mass must match the reference regardless of whether a particular metric notices. Two order traps: massFloor must be computed BEFORE the subtraction, and the subtraction must be a post-pass so the compound tensor survives. One open confound to carry forward: §96.4 point 3 states that step 7 (§86) is NOT de-confounded by this fix — its gate is up_rms on free running, not resync slope — so step 7 has to be re-measured on the fixed build.

#### 9. wm4_inertia_from_box — §93 chassis inertia lever

- **What:** Default 0 = keep the inertia tensor Jolt derived from the chassis compound shape; 1 = replace it with the tensor ODE would compute from the chassis box, so the shadow's rotational response matches the reference exactly. The §93 line runs unconditionally at build time and reports both tensors side by side plus their ratio, so the lever's cost is visible whether or not it is engaged. The ODE box tensor is the standard solid-box formula on the FULL dimensions with a leading m/12, verified exactly on two vehicles from the log: mass=132.0, box 3.00x2.00x8.00 gives (748.0, 803.0, 143.0) = 132/12·(4+64), 132/12·(9+64), 132/12·(9+4); mass=100.0, box 6.00x1.00x3.00 gives (83.3, 375.0, 308.3). The observed ratios are the reason the lever exists: Scout01 (7.62, 0.62, 1.56), Molokovoz01 (1.06, 0.75, 2.15), Bug01 (0.92, 0.84, 1.04) — the compound tensor is off by more than 7x on one axis of one vehicle.
- **Source:** formats.tsv 0x101dca18; kraken-20260727-1527.log lines 38, 665, 716; docs/recovered/README.md line 16 names it "§93 inertia lever"; sec96-wheel-mass-fix.md cites §93 as precedent for keeping a correctness default despite a null metric; sec95-force-site-sweep.md §95.5 corrects §93.1 (m_massTranslation is ported via _SetMassCenter in _Construct, not via dMassTranslate, which genuinely does not exist)
- **Constants:** default 0, bounds [0,1] (integer, authoritative). Box inertia formula m/12·(dy²+dz²), m/12·(dx²+dz²), m/12·(dx²+dy²) on full dimensions. No other constants.
- **Log line:** docs §93: chassis inertia (%s) mass=%.1f | JOLT(compound) = (%.1f, %.1f, %.1f) | ODE(box %.2fx%.2fx%.2f) = (%.1f, %.1f, %.1f) | ratio = (%.2f, %.2f, %.2f)
- **Pitfall:** The mass field in this line is the PRE-subtraction chassisMass — the whole-vehicle mass — proved by the timestamps in the log (§93 at 15:27:07.996 reads mass=132.0, §58 one millisecond later reads chassisMass=132.0, chassisMassFinal=96.0). So §93 runs before the §96 post-pass, and the §96 post-pass then scales whatever tensor is in place by the same single factor. Get the ordering wrong and either the box tensor is computed on the reduced mass (wrong reference) or the §96 scaling is applied twice.

#### 10. wm4_joint_at_mount — §75 constraint anchor placement

- **What:** Default 0. Chooses where the SixDOF constraint's shared anchor (mPosition1 = mPosition2) sits. #### 11. resync.py — the §82 divergence instrument (replaces divergence_rate.py)

- **What:** Parse every `docs §82: resync` line after the last build; each line is one resync interval with three numbers that matter: upMax (deg of attitude divergence accumulated in the interval), posMax (m), and odeTiltPath (deg of ODE's own attitude travel over the same interval = the perturbation the interval saw). ## Cluster: spin-steer

### Summary

This cluster is the seam between Jolt's collision pipeline and the untouched `wheelmodel_core.hpp`: plan step 3 (harvest buffer + parallel step listener, forces still zero) and step 4 (turn the forces on, un-sensor the RIM sub-shape, hard core live). Three artefacts constrain it much harder than the plan alone. (a) The vendored Jolt in `F:\Kraken\extern\joltphysics` matches every line number the plan cites (`PhysicsSystem.cpp:786` gravity consumes the force accumulator, `:1101` picks `mMaxSeparationDistance` off the *body* sensor flag, `:2088` honours a listener-set per-pair `mIsSensor` on the CCD path, `:2541-2542` `ResetForce`/`ResetTorque`), so those facts can be relied on verbatim — but `OnContactValidate` in this version takes **no `ContactSettings`**, so the plan's "set `settings.mIsSensor` in OnContactValidate/OnContactAdded/OnContactPersisted" is wrong for the first of the three. (b) `docs/recovered/binary/kraken-20260727-1527.log` shows the lost implementation clamped the reprojected penetration to τ **at the seam** (`pen=0.01000 penRaw=0.03329 tau=0.01000`), which is what actually produced the `F_n ≤ k_t·τ = 1200 N` bound — the hard core did *not* hold penetration to τ (penRaw ran to 3.3τ with `wm4_hardcore=1`), so the plan's claim that the bound is geometric is false in practice and the clamp is load-bearing. (c) The bound is on the spring term only; the core's `−c_t·v_n` damping rides on top and was measured breaching it (`ratio=1.04  *** EXCEEDS GEOMETRIC BOUND ***`), so step 4's acceptance criterion has to be a logged ratio, not an assert. The listener runs inside `JobStepListeners` with **positions read-only** (broadphase runs concurrently), velocities read/write, bodies may be activated but not deactivated, and `context.mDeltaTime` is the *sub-step* dt — that is the `dt` the core must see. Sub-stepping is an outer loop of `Update(dt/n, 1, ...)` on the main thread, not `Update(dt, n, ...)`, because the harvest parity flip and the pre-step motor/snapshot work must happen between sub-steps; `wm4_max_dt` / `wm4_max_substeps` gate it and `substeps_per_frame` reports it. Wheel bodies are identified in the callback by a tagged 64-bit `UserData` — and because the existing `VehiclePushbackContactListener` blindly `reinterpret_cast`s `UserData` to `hta::ai::Vehicle*`, that listener must be taught to reject the tag or it will fabricate a garbage `Vehicle*` the first time a wheel touches a kinematic mirror. Finally, §3.5's four silent meaning changes (`m`, `P.inertia`, `v_p`, `pen`) all land in this cluster's code, and a fifth consequence follows from them: `jolt_wm_max_g * m * g` shrinks ~4.5× when `m` goes from sprung to unsprung, so the §44.1-2/§50 friction cap must simply not be ported into the mode-4 seam — which pulls plan step 7's removal forward to step 4 whether or not that is intended.

#### 1. Tagged wheel UserData + O(1) registry

- **What:** Give every wheel body a discriminated 64-bit UserData so the contact callback can identify it with no dictionary and no lock. - **Source:** plan §2.1 line 84 (`mUserData` — тегированный uint64 `{kind=WHEEL(1), vehicleSlot, wheelIndex}`, O(1) идентификация в колбэке без словарей и блокировок); existing tagging at source/fix/joltshadow.cpp:1059 and :3257

#### 3. WheelHarvest record and double buffer

- **What:** Per-wheel lock-free record buffer, 16 slots, double-buffered by step parity. Layout from the plan: `struct Rec { float p[3]; float n[3]; float depth; uint32_t bodyId; uint8_t sub; }; struct WheelHarvest { std::atomic<uint32_t> count; Rec c[16]; }; WheelHarvest buf[2];`. Write path is `uint32_t idx = count.fetch_add(1, std::memory_order_relaxed); if (idx < 16) write;` — `count` is deliberately allowed to run past 16 so the excess is the overflow figure. `p` is the world-space contact point on the **surface** side (`manifold.mBaseOffset + mRelativeContactPointsOn1[i]` when the wheel is body 2, On2 when the wheel is body 1); `n` is the manifold normal reoriented to point **out of the surface toward the wheel** (`mWorldSpaceNormal` as-is when the wheel is body 2, negated when the wheel is body 1); `depth` is `manifold.mPenetrationDepth` kept for diagnostics only; `sub` is 0=TYRE / 1=RIM. Buffer written = `buf[step & 1]`, buffer read = `buf[(step ^ 1) & 1]`; the reader zeroes the buffer it is about to hand over (or the parity flip does), so no clear pass is needed.
- **Source:** plan §3.2 lines 143-153 (verbatim struct at lines 146-149, fetch_add rule at 152, «Двойная буферизация по чётности шага — сброс не нужен» at 153); Jolt ContactManifold layout, extern/joltphysics/Jolt/Physics/Collision/ContactListener.h:32-37

- **Log line:** none
- **Pitfall:** `mPenetrationDepth` is negative for speculative contacts (`spec_contact_dist=0.02` is live in kraken.ini). Do NOT filter records on depth>0 at harvest time — a speculative record is still a perfectly good sample of the surface plane, and the reprojection is what decides survival. Second trap: a manifold carries ONE normal and ONE depth but MANY points, so one manifold yields several Recs that share `n` and `depth`.

#### 4. Parity ownership: who flips `step`

- **What:** The parity counter must be advanced exactly once per physics step, on the main thread, BEFORE `PhysicsSystem::Update` is called — never inside the listener. Concretely: a single global `g_harvestStep` incremented in the sub-step loop immediately before each `Update()` call, read by both the callback (write buffer) and the listener (read buffer).
- **Source:** plan §3.4 lines 167-190 (job-graph order: JobStepListeners → JobApplyGravity → JobFindCollisions → Solve), §3.2 line 150
- **Constants:** none
- **Log line:** none
- **Pitfall:** This is the single strongest argument for the sub-step loop being N calls of `Update(dt/n, 1, …)` rather than one `Update(dt, n, …)`: with inCollisionSteps>1 the main thread never regains control between collision steps, so parity cannot be flipped and the pre-step snapshot cannot be refreshed.

#### 8. Depth reprojection and the tyre band geometry

- **What:** Per wheel, per surviving record: `penRaw = R − dot(c_now − p_anchor, n̂)` with `c_now = wheelBody->GetCenterOfMassPosition()` (equal to the wheel centre — both spheres sit at `Vec3::sZero()`), then `pen = min(penRaw, τ)` and drop the record if `penRaw <= 0`. #### 10. Applying the force to the WHEEL body

- **What:** In `OnStep`, after the core returns, call `wheelBody->AddForce(F, p)` — the two-argument overload at Body.h:187 — on the CACHED `JPH::Body*`, never via `BodyInterface::AddForce(BodyID, …)` which locks. #### 15. Sub-stepping loop

#### 7. Wheel-mass double count: the bug the re-implementation must not re-create

- **What:** This is the one item that is not 'port something new' but 'do not reproduce a defect'. Cause chain, all disassembled: `ai::Vehicle::GetMass()` (RVA 0x1D5BD0) returns chassis-body mass PLUS every wheel's mass (loop over m_wheels, 0x150..0x154, stride 0x24, m_wheel at +0x20), while the chassis body's own mass is set by RefreshMass from `Vehicle::_CalcMassForBody` and contains NO wheels. The current source already sets the Jolt chassis to the total: source/fix/joltshadow.cpp:1025 `bodySettings.mMassPropertiesOverride.mMass = std::max(vehicle->GetMass(), 100.0f);`. As soon as mode 4 also creates one dynamic body per wheel, the wheels are counted twice: Bug01 168.0 vs ODE 132.0 (+27.3%), Molokovoz01 211.0 vs 167.0 (+26.3%), Scout01 106.0 vs 100.0 (+6.0%). Mode 2 creates no wheel bodies and is therefore correct.
The fix, exactly as it shipped (§96.1) - build it in from the first line of `BuildWheelBodies`, do not add it later:
  1. Compute the mass floor FIRST, on the PRE-subtraction chassis mass (= whole-vehicle mass): per-wheel `mass = max(unsprungMass, chassisMass / 40.0f)`. This ordering is deliberate and load-bearing: it makes the floor a guard against a pathological wheel/vehicle ratio and removes the circular dependency.
  2. Accumulate `wheelMass` across the loop.
  3. AFTER the loop, scale the chassis body's mass AND its inertia tensor by the SINGLE factor `(chassisMass - wheelMass) / chassisMass`. Do it as a post-pass on the already-created body, not at CreateBody time, so the compound-derived tensor from §23.10 is preserved - Jolt got the SHAPE of the tensor right, only the magnitude was wrong, and the tensor is linear in mass because the chassis shape did not change.
  4. Refuse instead of breaking silently: if `wheelMass >= 0.90 * chassisMass`, skip the subtraction and warn. Driving the chassis toward zero mass turns a solver blow-up into 'the fix made it unstable'.
  5. Lever `wm4_chassis_mass_excl_wheels`, default 1 (the CORRECT behaviour); 0 restores the bug and exists only for measurement.
Also: the exact same number must reach `wm::GeneralizedContactForce`'s `m` and `P.inertia` (plan §2.1 line 78, §3.5) - the floored wheel-body mass, not `vehicle->GetMass()/numWheels`.

## Cluster: findings-first

### Summary

This cluster rebuilds plan steps 1 and 2: extract the per-wheel settings into a POD, create one dynamic Jolt body per wheel, and hang it off the chassis with one JPH::SixDOFConstraint, plus the layer/group/filter plumbing that keeps a vehicle from colliding with its own wheels. Almost all of it is recoverable exactly rather than by inference: the last Stage-1 DLL's BuildWheelBodies function was located through the docs §75 format string at 0x101dc230 and disassembled end to end (0x100328b5-0x100347d5), and every constant below was read out of .rdata rather than guessed. The body is a StaticCompoundShape of two concentric spheres (R and max(R-tau,0.01)), object layer 4, mass max(hw->GetMass(), chassisMass/40), inertia a disc diagonal (0.5mR^2, 0.25mR^2, 0.25mR^2) with local X = axle, mMaxAngularVelocity forced to 300, friction/restitution/both dampings zeroed, manifold reduction cleared on the Body, and a 'WHL' tagged user data. The constraint is WorldSpace with mAxisX = the axle and mAxisY = the forward vector orthonormalised against it, ESwingType::Pyramid, TranslationX/Y fixed, TranslationZ limited to (-fraction*range, +(1-fraction)*range) about spawn with a StiffnessAndDamping Position motor at target zero, RotationY fixed, and RotationX/RotationZ fixed at step 2 but already written behind the wm4_spin and wm4_steer gates that steps 5 and 6 flip. Two places where the surviving plan is superseded by the shipped binary are called out explicitly: the constraint anchor defaults to the wheel centre, not the chassis mount (wm4_joint_at_mount=0), and the travel limits are a signed split around spawn, not the absolute [minLen, maxLen] pair the plan names. The §96 finding is built in from the start as a post-pass that scales the chassis body's mass and inverse inertia by one factor, with a 90% refusal guard, because Vehicle::GetMass already includes the wheels. Step 2 ships with both sub-shapes sensor and the old StepWheelModel path still driving the chassis; its whole acceptance case is the pair of docs §58 log lines plus the §60 sag guard.

#### 2. Per-wheel sign derivation: spinSign and steerSign

#### 16. Shared contact torque cap (steer motor limit and handbrake limit)

- **What:** One per-wheel scalar per frame, in newton-metres, used as mMaxTorqueLimit for BOTH the RotationZ steering motor and the RotationX handbrake motor - the live log shows the identical value in the §68 cap field and the §67 cmdTq field on the same wheel in the same frame (3020Nm on wheel 0, 3049Nm on wheel 2, at 15:27:10.787). - **Source:** live log docs §68 cap field and docs §67 cmdTq field, correlated frame by frame with docs §66 fnGround/fnTotal and docs §58 springF; the recovered config key wm4_contact_torque_cap (jolt_harness, default 0, min 0, max 1, member +0x500) names this mechanism
- **Constants:** Floor = m_vehicle*g*R, established to 0.1% on both axles of Bug01 (815/0.629 = 1295.7 and 823/0.635 = 1296.1 vs 132.0*9.81 = 1294.9). The load-dependent term is NOT established - see unknowns.
- **Log line:** docs §68: steer (%s) w=%zu steerable=%d commanded=%.3f rad measured=%.3f rad err=%.2f deg steerSign=%+.0f steerTq=%.0fNm cap=%.0fNm sat=%.2f

### Stated unknowns

- The load-dependent part of the shared contact torque cap. The floor is nailed (m_vehicle * g * R, exact to 0.1% on both axles of Bug01), and at tyre-band saturation the cap approaches ~4800 N * R, but no single formula fits all 20 correlated samples: cap/R minus m*g divided by the logged fnGround gives 2.6, 2.9, 3.0, 3.1, 3.5, 3.7 across frames, and a pure multiplicative model gives 4.0-6.2. The per-frame log samples the last substep while the cap is computed elsewhere in the frame, so the driving F_n is not observable. Needs a decision (candidates: max(m_veh*g, k*F_n_grip) or m_veh*g + k*F_n_peak) plus a fresh instrumented run that logs the cap and its input in the same place.
- What wm4_contact_torque_cap (jolt_harness, default 0, min 0, max 1) actually gates. The config that produced the live log has it at 0 and finite caps are still present on both the steer motor and the handbrake motor, so the key gates something additional - most plausibly a cap on the tyre contact torque fed into the spin DOF (the tyreNm field of §70.1) rather than the motor limit. Not determined by any string.
- The steering Position motor's spring settings. The plan says ESpringMode::FrequencyAndDamping, "~20 Гц / ζ=1" with a tilde, and no format string, config key or log field carries either number. The ±35 deg limit and the torque cap are established; the spring stiffness and damping are not, and they set how fast the wheel follows m_steerRadians between the stop and the cap.
- The service-brake mechanism and its torque scale. The plan prescribes SetMaxFriction(RotationX, brake * maxBrakeTorque); the handbrake demonstrably used a different route (velocity motor to zero). maxBrakeTorque appears in no recovered artefact, and the only brake value that ever occurs live is 0.01, the idle self-braking floor, so the shipped braking behaviour was never exercised in the surviving log.
- What the RotationX motor state is for a non-driven wheel. Every wheel in every logged vehicle has driven=1, so the free-rolling case (motor Off? Velocity with zero limit?) is unobserved, as is what the gearbox's nDriven divisor does when only some wheels are driven.
- Where §71's reflected drivetrain inertia is applied - added to the wheel body's rotational inertia (requiring a mass-properties rewrite on every gear change) or only to the core's P.inertia - and the exact expression behind I_refl. wheelmodel.engine_inertia's default, min and max are not recoverable (float rows in config-members.txt are stale); only its shipped value 0.0 and its position in the [wheelmodel] section order are known.
- Whether the motor targets are re-written per substep when sub-stepping is active. wm4_max_substeps=8 exists but wm4_max_dt=0.000000 in the shipped config, so sub-stepping was off in the run that produced the log and the interaction is unobserved.
- The ±35 deg steering limit itself. hta::ai::Wheel::STEERING_LIMIT has no recovered value (joltshadow.cpp:135-140 says so explicitly), the ODE reference imposes ±pi on steered wheels and 0 on unsteered ones (§94.2), and the shadow's 35 deg is an invention that the live log shows the wheel resting against. It needs either a real value from the game data or an explicit decision to keep it as a swept constant.
- GetMaxTorque()'s per-vehicle source. driveTorque is reproduced exactly as GetMaxTorque()*ratio*diffRatio (Bug01 implies GetMaxTorque() = 50 Nm), but the accessor reads a cabin part's field and no MaxTorque attribute appears on the Bug prototype - so which part supplies it, and what happens when the cabin is swapped mid-session, is not established here.
