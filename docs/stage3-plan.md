# Stage 3 — план: AI-машины тоже едут на Jolt

Провенанс: запрошено пользователем после вопроса «переходим к Stage 3?» (ответ — не сразу, два
именованных пункта Stage 2 остаются открытыми) и явного запроса «пиши план Stage 3». Формат тот
же, что у `docs/stage2-plan.md`. Определение Stage 3 — `docs/jolt-integration-techanalysis.md`
§5/§14: до `ai_count` AI-машин ОДНОВРЕМЕННО с игроком получают собственный `ShadowState` и (при
`apply=1`) реально ведутся Jolt, не только игрок. Требует `player_only=0` — двойной opt-in,
`ai_count>0` сам по себе ничего не значит, пока `player_only=1` (дефолт).

## -1. Критическая находка и исправление (при попытке Шага 5): краш на смерти AI-машины

Первый прогон Шага 5 (долгая смешанная сессия, `player_only=0`, 8 повторов) реально уронил игру
на 4-м повторе — `access violation reading address 0x00000000`. Трассировка стека (через
пересборку `kraken.dll` с `/MAP` для получения символов по адресам из краш-репорта):
`StepSceneHook → UpdateShadow → UpdateOneVehiclePreStep`, крах внутри вызова `BuildShadow` при
ребилде AI-тени. Логу непосредственно перед крахом предшествовали `Shadow (ai5): a wheel present
at build time is now gone/replaced, rebuilding` → `Shadow build skipped (ai5): vehicle has no
wheels` → `Shadow (ai6): ... rebuilding` → краш, вперемешку с потоком `schwarz`-логов
(пересчёт стоимости машины) — характерный признак уничтожения машины в бою.

**Причина.** `g_aiTargets` (`joltshadow.cpp:643`) — вектор `hta::ai::Vehicle*`, собственный
комментарий прямо говорит «fixed at selection time»: набор фиксируется один раз при выборе
(`InitAiShadowsIfNeeded`, пересканирование только при смене машины ИГРОКА — см. §0 ниже,
это было названо открытым пробелом ещё до прогона) и **разыменовывается каждый кадр без проверки
живости**. Тот же класс опасности, от которого в этом же файле explicitly защищается
`VehicleMirrorEntry` (комментарий: «never dereferences a stale Vehicle* without a fresh scan
confirming it's still live») — свежим сканом каждый кадр в `MirrorOtherVehicles`. Эта защита не
была применена к `g_aiTargets`. Когда AI-машина в `g_aiTargets` гибнет посреди сессии, указатель
становится висячим, и `UpdateOneVehiclePreStep`/`BuildShadow` продолжают читать через него.

**Исправление.** Новая `GetCurrentlyLiveVehicles()` — один свежий скан `ObjContainer` за кадр (тот
же паттерн, что уже использует `MirrorOtherVehicles`), и проверка `g_aiTargets[i]` на членство в
нём ПЕРЕД вызовом `UpdateOneVehiclePreStep` в `UpdateShadow`; если машина не живёт — `aiLive[i] =
false` без единого обращения к `g_aiTargets[i]` в этом кадре (что автоматически исключает и
post-step, уже гейтованный тем же `aiLive[i]`).

**Проверка.** Пересобрано, задеплоено, тот же сценарий (8 повторов) повторён: **0 крашей, 0
таймаутов**, все 8 повторов дошли до конца. `ai5/ai6/ai7` действительно перестали отчитываться
около 6-го повтора (та же реальная гибель машины) — но теперь штатно, без падения: 0 non-finite, 0
срабатываний предохранителя на всём протяжении, игрок и `ai0-ai4` продолжили работать чисто.

## 0. Инвентарь

**Что уже реализовано и как (§14 техотчёта, `source/fix/joltshadow.cpp`):**

| механизм | где | статус |
|---|---|---|
| Отбор AI-машин | `InitAiShadowsIfNeeded` — первые `ai_count` живых `Vehicle*` из `hta::ai::CServer::m_pObjects`, простой скан, НЕ XML opt-in (см. §14.1: прецедент `KVehicle` признан нерабочим — сабмодуль без `CLASS`/`END_CLASS`, хук `meta::Init` не вызывается, фабрика конструирует не тот тип) | реализовано, упрощённая версия |
| Пересканирование | только при смене машины игрока (тот же сигнал, что путь игрока) | реализовано; **НЕ** пересканирует (не заменяет погибшую машину новой) при спавне/смерти AI-машины посреди уровня — по-прежнему открытый пробел (меньше живых AI-теней со временем), но с §-1 больше не крашится: гибель машины теперь безопасно детектируется каждый кадр (`GetCurrentlyLiveVehicles`) и просто выключает эту тень, а не роняет игру |
| Коллизионные группы | игрок = 0, AI[i] = i+1 (`UpdateOneVehiclePreStep(..., collisionGroupId)`, joltshadow.cpp:6359) — у каждой машины СВОЯ подгруппа, self-collision внутри одной машины выключен, между разными машинами — включён | подтверждено чтением кода в этой сессии, не смоук-тестом |
| Write-back для AI | тот же `UpdateOneVehiclePostStep`, что и у игрока — ветвление по `state.wheelBodyMode` (Bug #1/#2 фиксы Stage 2) применяется к AI автоматически, отдельного AI-пути нет | код общий; **не проверено под wheelmodel=4** (см. ниже) |
| Гейт применения | `aiAllowApply = config.jolt_apply.value != 0` — ПРОЩЕ, чем у игрока (там ещё `player_only==0 \|\| bIsControlledByPlayer`); для AI это лишнее, т.к. `ai_count` уже требует `player_only=0` | асимметрия намеренная, не баг |
| Двойное представление | `MirrorOtherVehicles` (кинематическая копия для НЕ-Jolt-машин, чтобы игрок их не проходил насквозь) явно исключает машины из `g_aiTargets` (joltshadow.cpp:5559-5560) — не задваивается | подтверждено чтением кода |
| Лимит | `kMaxAiShadowsPerFrame = 128`, `ai_count` зажат в конфиге 0..128 | — |

**Критически важно — что из этого протестировано и когда:**

§14.4 смоук-тест (`apply=1 player_only=0 ai_count=3`, 25+с, 3 машины, 0 срабатываний, div=0.000м)
— **написан и пройден ДО wheelmodel=4**. И описание («три параллельных `VehicleConstraint`»), и
исторический контекст (весь sec94-123, включая обе критические находки Stage 2 — Bug writeback-
no-op и Bug незателепортированных колёс — появились уже ПОСЛЕ этого теста) означают: тест
валиден для нативных режимов 0/1/3, но **ничего не говорит о wheelmodel=4** — единственной
модели, которую весь этот план (sec94-123, Stage 2) вообще проверял. Под wheelmodel=4
одновременная работа нескольких AI-машин **ни разу не запускалась**.

**Именованные, ещё не проявившиеся риски (не выдуманы — прямо в коде/техотчёте):**

1. **§107.8-класс утечки для AI-ребилда.** Комментарий у `InitAiShadowsIfNeeded`
   (joltshadow.cpp:5499-5505) прямым текстом: заброшенные тела колёс старых AI-теней сохраняют
   `'WHL'` UserData со СТАРЫМ harvest-слотом и продолжают писать контакты в буфер, который читает
   пересобранная тень — тот же механизм, что нашли на variant-тенях (§107.8: контакт в 319
   радиусов колеса, `penRaw=-18.9м`). Для AI-пути «не наблюдалось падающим, потому что нужен
   режим 4 плюс ребилд AI-теней» — именно то сочетание, которое Stage 3 под wheelmodel=4 впервые
   создаёт.
2. **Конвойная кинематика.** §14.3: `Formation::_UpdateVelocity` (ведущая машина конвоя) не
   дизассемблирована в этой сессии — риск не устранён, просто не проверен.
3. **Throughput/perf.** §15 прямым текстом: Stage 3 тестировался на корректность (2-3 машины), не
   на throughput/latency под нагрузкой на десятках машин. wheelmodel=4 — не встроенный
   `VehicleConstraint`, а per-wheel реальные тела + рейкасты + моторы (§54/§67/§68 и т.д.) КАЖДЫЙ
   кадр на КАЖДОЕ колесо КАЖДОЙ тени — заметно тяжелее по конструкции, чем то, что измерял §14.4.
4. **Обоюдный Jolt-Jolt таран.** `ram_test` (Stage 2 Шаг 2) проверял только игрок-на-Jolt против
   ODE/кинематической цели. AI-машина-на-Jolt в роли ЦЕЛИ тарана (`ApplyRamPushback` с обеих
   сторон реально Jolt-ведомые) — не проверено вообще.
5. **Потолок скорости на масштабе.** `wm4_max_speed_mps=100` (Stage 2 §2.5) откалиброван на
   одну машину в скриптованном сценарии. AI-вождение (решения `_KeepThrottle`/`_CalcSteeringForce`
   в реальном трафике) может вести себя агрессивнее/иначе — неизвестно, чаще или реже это будет
   задевать потолок на масштабе.

**Не заново открываем (§14.3, уже закрыто дизассемблированием, не зависит от модели колёс):**
AI-логика принятия решений (`_CalcSteeringForce`/`_KeepThrottle`) читает те же no-cache
`GetPosition`/`GetLinearVelocity`, что уже проверены безопасными для игрока, и выполняется строго
ПОСЛЕ синхронизации в одном и том же вызове `ai::CServer::Update` — AI видит консистентное
состояние каждый кадр. `bIsUpdatingByODE` нигде не используется в AI-пути — трогать не нужно.

## 1. Рамка приёмки

Как и Stage 2 (§1 того плана): играбельность, не побитовое совпадение с ODE. Принятые в бюджет
пункты sec122/123 и Stage 2 §2.5 (потолок скорости, origin/COM-константа расхождения) сюда не
переносятся как блокеры. Дополнительно для Stage 3: качественная (человеческая) оценка трафика
— вне охвата этой автоматизированной части плана, как и в Stage 2 §2 Шаг 1 гейты 2-3.

## 2. Шаги

### Шаг 1 — Смоук-тест под wheelmodel=4 (маленький ai_count)

**Что:** повторить именно тест §14.4 (`apply=0/1 player_only=0 ai_count=3`), но с
`wheelmodel=4, wm4_steer=1` — впервые. Сначала `apply=0` (shadow-only, убедиться что несколько
`wheelBodyMode`-теней вообще строятся и не роняют игру и не дают NaN на живом AI-трафике), затем
`apply=1` (реальное вождение AI на Jolt).

**Гейт продолжения:** N машин строятся (лог «Stage 3: selected N AI vehicle(s)»), 0 non-finite,
0 (или редкие, самозаживающие) срабатываний speedcap, расхождение ограничено и не растёт
неограниченно ни у одной из машин.

### Шаг 2 — AI-ребилд (проверка §107.8-класса утечки)

**Что:** несколько смен машины игрока подряд в одной сессии (`pin_vehicle` несколько раз, как в
`discover_vehicles.py`) при `ai_count>0, apply=1, wheelmodel=4` — каждая смена триггерит
пересканирование и ребилд AI-теней. Ищем именно то, что комментарий в коде называет: контакт от
заброшенного тела старого ребилда (аномально далёкий `penRaw`, скачок расхождения без видимой
причины на новых тенях сразу после ребилда).

**Гейт продолжения:** ни одного аномального контакта/скачка расхождения, коррелирующего по
времени с ребилдом; число живых тел после N ребилдов не растёт линейно с N (не копится мусор).

### Шаг 3 — Масштаб (throughput/perf)

**Что:** поднимать `ai_count` от малого к большему (например 8 → 32 → 128, до
`kMaxAiShadowsPerFrame`), смотреть на частоту срабатывания предохранителей и — если
`testharness perfmon` даёт кадровое время — на деградацию FPS при росте числа wheelmodel=4-теней
одновременно. Это первое реальное измерение стоимости multiple wheelmodel=4 shadows; §15
прямо говорит, что раньше такого измерения не было.

**Гейт продолжения:** нет катастрофической деградации кадра при разумном `ai_count`; если есть —
назвать порог, после которого играбельность страдает, а не молчать об этом.

**Результат (после первоначальной попытки на save 00000009, где реально нашлось лишь ~8 AI —
см. ниже).** Отдельно найден save `00000010` со **74 реальными AI-машинами** рядом с игроком
(через перебор всех 11 сейвов) — первый настоящий тест масштаба. `apply=1, player_only=0,
wheelmodel=4, ai_count=128` (реально выбрано 74/74), 45с наблюдения, машины предоставлены сами
себе (throttle игрока = 0, никакого скрипта):

- **0 крашей, 0 non-finite, 0 срабатываний speedcap** — ни разу, ни на одной из 75 меток
  (игрок + 74 AI) за 45с.
- Расхождение ограничено на ВСЕХ 75 метках (0.36-1.6м) — запись работает корректно на полном
  масштабе, не только на 3-8 машинах, что проверялось раньше.
- **fps просел до ~24-26** (кадр ~39-42мс) — против ~137-149fps на 0-8 AI-тенях (Шаг 3, первая
  попытка). Это первое реальное измерение стоимости масштаба: ~74 wheelmodel=4-тени
  одновременно стоят на порядок дороже кадра, чем единицы теней — ожидаемо, раз каждая тень
  считает per-wheel рейкасты/моторы каждый кадр, а не единый `VehicleConstraint`. На таком fps
  играть уже некомфортно, хотя физически всё стабильно.
- Число тел по меткам — только 5 или 7 (шасси+4/6 колёс), без аномалий.

**Вывод по шагу.** Корректность на масштабе подтверждена чисто (это был главный риск шага —
устоит ли масштаб вообще). Производительность — честно назван порог: где-то между ~8 и ~74
одновременными AI-тенями кадр деградирует с «незаметно» (Шаг 1) до «уже некомфортно» (~25fps);
точная граница не измерена (нет промежуточных точек 16/32 на этом сейве), это отдельный,
более мелкий пункт на будущее, не блокер самого факта работоспособности.

### Шаг 4 — Обоюдный Jolt-Jolt таран

**Уточнение по факту чтения кода (важная находка перед реализацией):** первоначальная
формулировка этого шага («проверить `ApplyRamPushback` при обеих Jolt-ведомых сторонах») была
основана на неверном предположении. `HandleContact` (joltshadow.cpp:6757-6796) явно и намеренно
пропускает пару, если `body1Dynamic == body2Dynamic` — комментарий: «both or neither dynamic -
native Jolt already resolves dynamic-vs-dynamic correctly». `ApplyRamPushback` существует
СПЕЦИАЛЬНО для пары Jolt-динамическое тело vs кинематическое зеркало (`MirrorOtherVehicles`) —
когда обе стороны реальные Jolt-тела (игрок и Stage-3 AI-тень), физику столкновения решает
нативный солвер Jolt напрямую, без этого кода, и так и должно быть. Реальный вопрос Шага 4:
не «сработает ли `ApplyRamPushback`» (по коду не должен и не сработает), а держит ли себя
устойчиво нативное Jolt-столкновение двух wheelmodel=4 машин (составной корпус + SixDOF колёса
с обеих сторон) — тот тип столкновения, что вообще ни разу не проверялся.

**Что:** `ram_test` с `ai_count`, достаточным, чтобы цель `FindOtherLiveVehicle` попала в число
`g_aiTargets` (тот же скан `ObjContainer`, что использует `InitAiShadowsIfNeeded` — при
достаточном `ai_count` первая найденная машина у обоих одна и та же). Смотрим НЕ на срабатывание
`ApplyRamPushback` (ожидаемо 0), а на стабильность обеих машин после удара.

**Гейт продолжения:** 0 non-finite и 0 (или редкие самозаживающие) срабатываний speedcap-гейта
на ОБЕИХ метках (player и ai-цель) после удара; расхождение ограничено с обеих сторон.

**Результат.** Три живых попытки (offset=15м/9с, 15м/25с, offset=5м/10с) с прямым замером 3D-
дистанции игрок↔ai0 по кадрам: цель (реальный AI, тот же индекс `g_aiTargets[0]`, что и `ai0`)
активно маневрирует и уезжает — во второй попытке дистанция росла МОНОТОННО 16.9м → 122.3м за
25с, ни разу не приблизившись; в третьей (минимальный отступ) ближайшее сближение 4.72м, но снова
разошлись к концу окна. Ни разу не зафиксировано реального контакта. Это тот же
методологический пробел, что уже был назван в Stage 2 Шаге 2 (`ram_test` — скриптованный прямой
подход без коррекции курса, не годится против реально маневрирующей AI-цели) — теперь
подтверждён во второй раз, с прямыми данными о расстоянии, а не предположением.

Что подтверждено чисто во всех трёх попытках: 0 non-finite, 0 срабатываний speedcap на ОБЕИХ
метках (player и ai0) при одновременном независимом вождении до 44с суммарно; `ApplyRamPushback`
корректно НЕ сработал ни разу (ожидаемо — обе стороны dynamic, см. уточнение выше). Но сам
заявленный вопрос шага — устойчивость НАТИВНОГО Jolt-столкновения двух wheelmodel=4 машин — по
факту НЕ проверен прямым наблюдением через `ram_test`: контакта просто не произошло.

**Добито (после находки Шага 3 про save `00000010`).** Раз `ram_test` не годится против реально
маневрирующей AI-цели, а плотный трафик (74 AI) сам по себе производит контакты (см. живые
`docs §23.4: live ram-damage call` в shadow-only прогоне при проверке загрузки сейвов) — прогнан
прямой 60-секундный прогон на `save 00000010`, `apply=1, player_only=0, wheelmodel=4, ai_count=128`
(74 реальных AI), без всякого скрипта, машины предоставлены сами себе. Попарные 3D-дистанции между
всеми 75 Jolt-динамическими шасси считались напрямую из `jolt com=[...]` в логах расхождения
каждого кадра.

**Результат — контакт зафиксирован, устойчивость подтверждена.** Минимальная дистанция за 60с:
**1.96м между `player` и `ai64`** — в пределах касания корпусов (типичная полуширина шасси
1-2м). Ещё 29 сближений <6м между разными парами AI-машин по всей записи (`ai45↔ai64`,
`ai2↔ai4`, `player↔ai72` и т.д.) — реальные столкновения в плотном трафике происходят часто, не
разово. **0 non-finite, 0 срабатываний speedcap-гейта за весь прогон**, включая моменты вокруг
всех зафиксированных сближений. Шаг закрыт: нативный Jolt-солвер держит dynamic-vs-dynamic
столкновение composite-шасси с SixDOF-колёсами устойчиво, без специального кода со стороны порта.

### Шаг 5 — Долгая смешанная сессия

**Что:** аналог Stage 2 Шага 3 (10×79с и больше), но теперь `player_only=0` — игрок И AI
одновременно на Jolt весь прогон. Смотреть на то же: рост срабатываний, рост числа тел (утечка),
плюс теперь ещё — рост числа тел ИМЕННО по AI-веткам (отдельно от игрока), раз §107.8-риск
специфичен для AI-ребилда.

**Гейт продолжения:** тот же, что Stage 2 Шаг 3 — ноль роста по обоим счётчикам.

**Результат.** Первая попытка реально уронила игру (краш на 4-м повторе) — найдена и исправлена
критическая находка §-1 (висячий указатель на погибшую AI-машину). Повтор после фикса: **8/8
повторов, 0 крашей, 0 таймаутов, 0 non-finite, 0 срабатываний предохранителя** на всём протяжении
(~2.9 мин). `ai5/ai6/ai7` перестали отчитываться около 6-го повтора (реальная гибель машины в
бою) — штатно, без падения. Число тел у выживших меток (`player`, `ai0-ai4`) стабильно все 8
повторов — утечки нет. Шаг пройден чисто С УЧЁТОМ фикса; без него Stage 3 был бы неиграбелен на
любой достаточно долгой сессии с боевым AI-трафиком.

### Шаг 6 — Итоговое решение

**Что:** по итогам шагов 1-5 — явный opt-in (`player_only=0, ai_count=N`) с названным безопасным
`N`, либо отчёт о том, что именно не прошло и почему рано.

**Вердикт.** Главный итог всего плана — не численный гейт, а сама находка §-1: у уже
существовавшей «упрощённой версии» Stage 3 (§14 техотчёта) был реальный, ни разу не пойманный
краш (висячий указатель на погибшую AI-машину), который ронял игру на ЛЮБОЙ достаточно долгой
сессии с боевым AI-трафиком — то есть Stage 3 был непригоден к использованию до этого плана,
несмотря на «готово» в заголовке §14. Найден и исправлен, подтверждён живым повтором (8/8, было
1/8 до фикса).

Помимо этого: Шаги 1 и 2 пройдены чисто (первый живой запуск нескольких wheelmodel=4 AI-теней
одновременно, и ребилд-утечка не проявилась за 5 попыток). Шаг 3 (масштаб) впоследствии добит на
`save 00000010` (74 реальных AI, найден отдельным поиском по всем 11 сейвам) — throughput
подтверждён чисто на полном масштабе (0 крашей/non-finite/speedcap за 45с), честно назван только
порог деградации fps (~137→~25 между 8 и 74 тенями, точная граница не измерена). Шаг 4
(обоюдный таран) также добит на том же сейве: 60с `apply=1` без скрипта, попарные дистанции по
всем 75 машинам показали реальный контакт (1.96м игрок↔ai64, ещё 29 сближений <6м между разными
AI) при 0 non-finite/speedcap за весь прогон — устойчивость нативного Jolt dynamic-vs-dynamic
столкновения подтверждена прямым наблюдением, методологическая яма `ram_test` обойдена через
достаточно плотный трафик вместо скриптованного сближения.

Рекомендация: явный opt-in (`player_only=0`), не дефолт. `ai_count` — корректность подтверждена
вплоть до 74 одновременных AI-теней, но комфортный по fps диапазон — до ~8-10 (заметная просадка
кадра начинается где-то между 8 и 74, точный порог не измерен). Два оставшихся, не блокирующих
сам факт работоспособности пункта на будущее: точный порог деградации fps между 8 и 74 (Шаг 3),
конвойная кинематика (§14.3, ни разу не задета ни одним шагом этого плана).

## 3. Откат

Тот же уровень, что Stage 2 §3: `player_only=1` (дефолт) мгновенно возвращает «только игрок» —
`ai_count` при этом становится инертным (см. joltshadow.cpp:6310-6314), пересборки не требует.
Отдельного отката именно AI-части (`ai_count=0` при `player_only=0`) тоже достаточно и ещё дешевле.

## 4. Что этот план сознательно не покрывает

- Production-путь через XML `Class="JoltVehicle"` (§14.1) — признан нецелесообразным в этом
  инкременте, простой скан остаётся текущим механизмом.
- Конвойная кинематика (`Formation::_UpdateVelocity`) — только назван как непроверенный риск
  (§14.3), не дизассемблирован и не протестирован в этом плане; если Шаг 1-5 не заденут ведущую
  машину конвоя, риск остаётся открытым, а не закрытым.
- Stage 4 (единый мир, contact bridge для оторванных частей) — по-прежнему отложен до
  профилирования (§15 техотчёта), которое Шаг 3 этого плана начинает, но не завершает.
- Два открытых пункта самого Stage 2 (человеческий плейтест Шага 1, прямая проверка
  `ApplyRamPushback` не через `ram_test`) — не блокируют написание/старт этого плана, но
  разумно закрыть параллельно, а не откладывать бесконечно.
- **Именованная, не устранённая хрупкость: слишком быстрое переключение уровней.** При переборе
  всех 11 сейвов с агрессивными паузами (~1.2с между `load_save.txt`) игра дважды падала БЕЗ
  поимки краш-хендлером Kraken (в отличие от §-1 — не тот же баг), с предшествующим паттерном
  «колесо игрока пробито 7000+ кадров подряд, раскачивающийся момент трения». С щедрыми паузами
  (встроенные тайминги `session.py`, ~14с+/переключение) на тех же 11 сейвах — не воспроизвелось
  ни разу. Не расследовано до конкретной причины (вероятно, смена уровня до полного оседания/
  разбора предыдущей Jolt-тени) — не блокер, потому что реальный игрок не переключает сейвы
  быстрее раза в несколько секунд, но стоит иметь в виду как открытый, некритичный пункт.
