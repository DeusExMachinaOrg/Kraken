# §126: "O" hotkey recovery ("выбраться из сложного места") под Jolt

## Повод

Живой репорт пользователя во время расследования §124 (Ural01 холодный пин под
`wm4_contact_constraint=1` зависает, колёса визуально под землёй, см.
`sec124-wheel-contact-constraint-plan.md` §124.11-124.13): штатный хоткей **O**
(`IM_CAR_GET_OUT_OF_DIFFICULT_PLACE`, `data/profiles/*/keybindings.lua:34`) в ODE вытаскивает
машину из сложного места, но под Jolt (`[jolt_harness] apply=1`) не делает ничего заметного.

## Причина клоббера (общая для обеих попыток)

Под `apply=1` `ApplyJoltToVehicle` (`source/fix/joltshadow.cpp:5287`) КАЖДЫЙ кадр читает
позицию/ориентацию/скорости Jolt-тела и штампует их на ODE-машину (`SetPositionSelf`/
`SetRotationSelf`, строки 5347/5363-5366). Любая native-функция, двигающая только ODE-тело,
теряет эффект в течение кадра — то же столкновение, что уже решено для `TeleportPlayerShadow`
(`source/fix/joltshadow.cpp:7441`, объявлена в `include/fix/joltshadow.hpp:14`): переставляет
именно Jolt-тело игрока, зануляет скорости, переинициализирует кэш подвески.

## Первая попытка — КРАШНУЛА живьём, откачена

Первый хук целился в **публичную** `Vehicle::GetOutOfDifficultPlace` (VA `0x005CBB00`) с
5-байтовым трамплином — по образцу уже существующего `CalcDamageToVehiclesHook`, но БЕЗ
верификации границы инструкций дизассемблером (в отличие от эталона, где это явно
задокументировано). Пользователь нажал O — игра упала:

```
=== UNHANDLED EXCEPTION === code=0xC0000005 addr=6BBB812B (kraken.dll+0x51812b)
Access violation writing address 0x86445AB8
Registers: ecx=0x529D5B18 esi=0x529D5B18 edx=0x00000000 ...
```

Разбор (capstone против реального `hta.exe`, `tools/lora`-стиль дисасм) вскрыл ДВЕ отдельные
ошибки:

1. **`GetOutOfDifficultPlace` — это ОДНА 7-байтовая инструкция**, не несколько мелких:
   ```
   0x005CBB00: mov byte ptr [ecx+0x4cc], 1   (7 bytes)   ; m_bMustGetOutOfDifficultPlace = true
   0x005CBB07: ret                            (1 byte)
   ```
   5-байтовый трамплин разрезал `mov` пополам — исполнение трамплина читало мусорные байты как
   инструкции, отсюда запись по случайному адресу и креш.
2. **Даже с верным трамплином это был бы no-op.** Функция всего лишь выставляет флаг
   `m_bMustGetOutOfDifficultPlace` (`Vehicle.hpp:226`) — саму перестановку она не делает.
   Реальная работа происходит ПОЗЖЕ, за пределами этого вызова, из `Vehicle::Update()`,
   опрашивающего флаг.

## Вторая попытка — работает, проверено дважды автоматизированно

Хук перенесён на **реальную рабочую функцию**: `Vehicle::_GetOutOfDifficlultPlaceInternal`
(VA `0x005E4740`, опечатка в имени — родная, `Vehicle.cpp:251`). Комментарий `NATIVE()` в игре
несёт пометку "TODO: must be `__usercall`" — но это неподтверждённая пометка САМОЙ игры, не
факт: реальный пролог по дизассемблеру —
```
0x005E4740: sub esp, 0xb8    (6 bytes)
0x005E4746: push esi         (1 byte)
```
чистый `__thiscall(this)`, `this` приходит в ECX и больше ничего не читается до сохранения в
ESI. Безопасная граница трамплина — **6 байт** (не 5, как у `CalcDamageToVehiclesHook` — там
граница была ровно 5 у совсем другой функции).

```cpp
using GetOutOfDifficultPlaceInternalFn = void(__fastcall*)(hta::ai::Vehicle*, void*);
static uint8_t s_getOutOfDifficultPlaceTrampoline[16];
static GetOutOfDifficultPlaceInternalFn Real_GetOutOfDifficultPlaceInternal = nullptr;

static void __fastcall GetOutOfDifficultPlaceInternalHook(hta::ai::Vehicle* v, void* /*edx*/) {
    Real_GetOutOfDifficultPlaceInternal(v, nullptr);
    if (v != nullptr && v == GetPlayerVehicle() && IsVehicleJoltAuthoritative(v)) {
        const bool moved = kraken::fix::joltshadow::TeleportPlayerShadow(v->GetPosition(), v->GetRotation());
        LOG_INFO("docs §126: O-key recovery ... re-seated Jolt shadow body=%d at pos=(...)", (int) moved, ...);
    }
}
```

`InstallGetOutOfDifficultPlaceHook()` копирует **6** байт в трамплин (не 5), пишет свой JMP
сразу за ними, зовёт `routines::Redirect(6, orig, ...)` — `Redirect` сам заполняет весь
переданный `size` байтами `0xCC` ДО записи 5-байтового JMP (`include/routines.hpp:20-33`), так
что лишний (шестой) байт на живой функции безопасно превращается в `int3`-заглушку — трамплин
использует СВОЮ отдельную, нетронутую копию тех же 6 байт.

### Новая возможность test harness'а (по прямому запросу пользователя)

Автоматически эмулировать реальное нажатие клавиши не удалось (`SendKeys`, затем `keybd_event` —
ни то ни другое не долетело до игры живьём в первой попытке; вероятная причина — тестовая
конфигурация управляет машиной через собственный drop-box, а не через настоящий impulse-слой
клавиатуры). Вместо этого добавлен детерминированный триггер: `get_out_of_difficult_place.txt`
(`source/fix/testharness.cpp`, `CheckGetOutOfDifficultPlaceTrigger`) — при записи файла вызывает
`vehicle->GetOutOfDifficultPlace()` НАПРЯМУЮ на машине игрока, тем же протоколом debounce, что и
`switch_vehicle.txt`. Это обычный, безопасно типизированный публичный вызов (не сырой
трамплин-хак) — риска краша от самого триггера нет.

### Проверка (два прогона, оба автоматизированные, оба чисто)

**Прогон 1 (безопасность, обычная машина).** Molokovoz01 на родном сейве `00000009`, спокойно
осевшая — `get_out_of_difficult_place.txt` триггерит, наблюдение 8с:
`process_survived=True triggered=True hook_fired=True`. Ни одного креша.

**Прогон 2 (целевой случай — реально зависший Ural01).** Тот же холодный пин, что и весь §124
(`wm4_contact_constraint=1`, сейв `00000009`), подтверждённо застрял (0 контакта 18с), затем
триггер:
```
crashed=False hook_fired=True recovered=False
docs §126: O-key recovery (_GetOutOfDifficlultPlaceInternal) re-seated Jolt shadow body=1
    at pos=(4668.36,258.84,1251.44)
```
Хук отработал корректно — вызвал настоящую нативную логику, переставил Jolt-тело туда же,
**без единого краша**. Но новая позиция почти не отличается от старой (застрявшей) — сдвиг на
~1-2м, машина по-прежнему не садится на колёса ещё 20с наблюдения. **Это не баг фикса, а предел
возможностей самой встроенной ODE-логики восстановления**: она рассчитана на типичное
«застрял между камней», не на настолько глубокую, специфичную для §124's Ural01-бага аномалию
(отдельное, всё ещё не до конца понятое расследование, см. §124.13) — восстановление сдвигает
машину туда, куда решает штатная логика, а не гарантированно вытаскивает из ЛЮБОЙ дыры.

## Итог

Механизм фикса подтверждён рабочим и безопасным дважды автоматизированно (0 крашей на обеих
проверках). Для обычных, штатных случаев застревания (то, для чего хоткей и предназначен)
должен работать корректно — переставляет Jolt-тело туда же, куда родная ODE-логика решает
переставить ODE-тело. Для экстремального случая §124's Ural01-бага восстановление технически
срабатывает, но недостаточно далеко перемещает машину, чтобы выбраться из зоны без контакта —
это ограничение глубины самого рекавери, отдельное от корректности этого фикса.

**Нужна дополнительная живая проверка пользователем на реальных, типичных ситуациях застревания**
(не искусственно воспроизведённый §124 Ural01-баг) — тестовые прогоны показывают, что механизм
работает, но субъективное «вытащило ли из ямы у камня» лучше всего проверить вживую.
