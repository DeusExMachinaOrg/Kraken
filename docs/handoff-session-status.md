## Что вообще сделано (весь путь, кратко)

Полная теханализ-доку `docs/jolt-integration-techanalysis.md` (17 разделов) — читать её, не эту
сводку, если нужны детали/код/адреса. Здесь только "что где лежит и что дальше".

1. **Stage -1/0** — Jolt засабмодулен, собран, слинкован; статика уровня (heightfield + дороги)
   экспортируется в Jolt при загрузке.
2. **Stage 1** — теневой `JPH::VehicleConstraint` для машины игрока, только логирует расхождение
   с ODE, не влияет на геймплей (`[jolt_harness] shadow=1 apply=0`).
3. **Stage 2** — Jolt реально ведёт машину игрока (`apply=1 player_only=1`), пишет результат
   обратно в ODE через `DisablePhysics()`+repositioning.
4. **Stage 3** — расширено на AI-машины через `ObjContainer` (`player_only=0 ai_count=N`).
5. **Stage 4** — сознательно НЕ начат (единый ODE/Jolt мир для тарана/оторванных частей) — не
   было оснований до профилирования (см. п.7 ниже).
6. **§8.5 auto-tuning** — подвеска (`susp_frequency`/`susp_damping`) и трение
   (`friction_long`/`friction_lat`) стали настраиваемыми параметрами `[jolt_harness]`, плюс
   работающий in-process coordinate-descent автотюнер (`autotune=1`). Найден и **дважды
   независимо подтверждён** (два разных манёвра) оптимум: `susp_damping=0.40` (частота и оба
   трения — дефолты Jolt). Значение уже применено в деплое.
7. **§17 профилирование** — реальные цифры FPS с/без Jolt на стресс-тест сейве (много AI-машин
   вокруг игрока): без Jolt 35.5 FPS, Jolt только на игроке 34.0 FPS (почти бесплатно), Jolt на
   игроке+16 AI 15.3 FPS (−57%, ~2.25мс на каждую доп. AI-машину). Подозрение (не подтверждено
   профайлером) — однопоточный `ApplyJoltToVehicle` write-back путь, а не сам
   `PhysicsSystem::Update()`.

## Инструменты, которые появились по пути (пригодятся дальше)

- **`fix::testharness`** — скриптованное вождение (`scenario.csv`/`trigger.txt`/
  `output_<token>.done` в `data/kraken_testharness/`), автозагрузка последнего сейва
  (`autoload_save=1`), **god mode напрямую через C++** (`god_mode=1` — обходит гейт
  `testcheat()`/`GetComputerName()` в `cheats.lua`, которым молча не работает "родной" `god()`
  на не-девелоперской машине), **wall-clock perf-монитор** (`perfmon=1` — fps/frame-time,
  независимо от Jolt).
- **`fix::joltshadow`'s AutoTune*** — in-process поиск параметров подвески/трения, переиспользует
  файловый протокол testharness, coordinate descent по 4 осям.
- **Урок про фокус окна**: автоматизированные прогоны через `Start-Process`/фоновый bash без
  явного вывода окна на передний план могут выглядеть как зависание (троттлинг кадров вне
  фокуса) — **всегда** делать `SetForegroundWindow`/`ShowWindow` через PowerShell `Add-Type`
  сразу после запуска `hta.exe`, если прогон автоматизированный. Паттерн уже был использован в
  этой сессии несколько раз, копипастить оттуда.

## Текущее состояние деплоя (`E:\HTA-Kraken`)

- `hta.exe` **не запущен**.
- `kraken.dll` — актуальная сборка со всем перечисленным выше (god_mode/perfmon включены в код,
  но выключены в ini).
- `data/kraken.ini` — безопасные "не тестируем" дефолты:
  ```ini
  [testharness]
  enabled=0
  autoload_save=0
  god_mode=0
  perfmon=0
  [jolt]
  enabled=1
  threads=0
  [jolt_harness]
  shadow=1
  apply=0
  player_only=1
  ai_count=0
  susp_frequency=1.500000
  susp_damping=0.400000    ; подтверждённый тюнинг, НЕ трогать без причины
  friction_long=1.000000
  friction_lat=1.000000
  autotune=0
  ```
  То есть: Jolt инициализируется и теневым образом сравнивается с ODE (`shadow=1`), но НИЧЕГО не
  водит (`apply=0`) — это самый безопасный "включено, но невидимо" режим для обычной игры.
- `data/kraken_testharness/` — может содержать мусор от последних тестов (scenario.csv с мягким
  манёвром из §16.6, старые output-файлы) — не мешает обычной игре, `testharness=0` значит хук
  вообще не ставится.

## Открытые вопросы / что можно делать дальше (ничего не начато, все — предложения)

1. **Профилировать `ApplyJoltToVehicle` предметно** (VTune/Superluminal/`JPH_PROFILE_ENABLED`),
   если когда-нибудь понадобится больше 16 одновременных Jolt-AI-машин — сейчас это только
   гипотеза по линейному масштабированию, не подтверждённый факт.
2. **Более тонкая настройка подвески/трения**, если текущий "обрыв" вокруг найденного оптимума
   (§16.5/16.6) окажется субъективно ощутим при живой игре — либо смягчить модель (multi-shape
   chassis вместо одной коробки), либо апгрейднуть поиск (CMA-ES/Nelder-Mead вместо coordinate
   descent).
3. **Stage 4** по-прежнему не начат и не считается срочным — актуализировать это решение, если
   появится профилировочный повод (см. п.1).
